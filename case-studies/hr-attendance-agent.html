Human-in-the-Loop Attendance Assistant

A controlled Microsoft 365 Copilot assistant that validates attendance messages and prepares a proposed tracker entry, while HR keeps every final decision.

Background

An HR team tracked absences in an Excel workbook. Each absence email needed the employee identified, the details checked against current attendance guidance, and a row entered in the tracker.

Problem

The process was repetitive and depended on careful reading. Manager-sent messages, missing dates and duplicate submissions made it easy to record the wrong thing.

My role

I designed and built the assistant during my internship, shared it with HR, and documented its inputs, rules, dependencies and test cases for the next maintainer.

Requirements

  • Read an absence message and pull out the employee, date and stated reason
  • Never guess when information is missing or unclear
  • Apply current HR attendance guidance
  • Produce a summary HR can read quickly and a proposed row in the tracker’s column order
  • Leave the approval and final attendance decision to a person

Solution architecture

The assistant is a controlled HR helper, not an autonomous attendance system. A conversational layer receives the message, extracts context, applies the rules in its instructions and knowledge sources, and prepares a proposal.

  1. Message or pasted email received
  2. Sender and employee context extracted
  3. Required fields validated
  4. Attendance guidance applied
  5. Proposed tracker entry and summary prepared
  6. HR reviews and approves
StageDetail
InputsAbsence message, sender, employee name, date, reason, organizational data, tracker structure, current HR guidance
ValidationEmployee identified and minimum tracker fields present; otherwise ask HR
ProcessingNormalize names and dates, separate the reporting employee from any manager sender, classify the event, summarize guidance
OutputHR-readable summary and a proposed tracker row

Security and responsible-AI considerations

Responsible AI principle: the assistant supports analysis and data preparation. It does not make final attendance decisions.

  • Access is limited to the HR users the agent is shared with.
  • Unclear input produces a question for HR rather than an assumption.
  • The output is a proposal. A person approves any change to the workbook.
  • It depends on stable workbook column names and current policy content, so both are documented.

Implementation process

  1. Defined the fields and column order the tracker requires.
  2. Wrote instructions covering extraction, validation, classification and output format.
  3. Connected the tracker structure and HR guidance as knowledge sources.
  4. Tested with realistic sample messages.
  5. Shared the agent with HR and documented access, dependencies and maintenance.

Testing

ScenarioExpected behaviour
Normal absence messageComplete proposed row and summary
Message sent by a manager for another employeeReporting employee identified separately from the sender
Missing dateAssistant asks HR for the date
Duplicate submissionDuplicate flagged for review
Guidance is unclearAssistant states the ambiguity and defers to HR

Outcome

HR received readable summaries and proposed tracker entries for review, with final decisions kept by people. At handoff the work was paused while HR feedback on accuracy and adoption was still being gathered, so the documentation lists what to re-test if the workbook or policy changes.

Lessons learned

  • Clear refusal rules matter as much as clever extraction.
  • Automation that touches people’s records should propose, not decide.
  • Documenting dependencies (file location, column names, sharing) prevents silent breakage later.
